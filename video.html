A creator shares one public Nostr tipping identity. Silent payments derive fresh recipient outputs without putting the reusable receiving address in each output. What you're seeing

  1. The creator problem — keep one public tipping identity without putting the same reusable receiving address in each payment output.
  2. Public binding — the existing demo npub is resolved from public relays; the browser verifies its signed binding (event 5a9f1252…). This is a genuine read-only interaction with the current deployed UI.
  3. Completed local proof — the complete earlier regtest clip shows construction, broadcast, mining, one receiver-scan match for 5000 test sats, and matching spending-key derivation. No spend of that output is demonstrated.
  4. Limits — the hosted signet demo is unfunded. Recipient-address reuse protection does not hide all payment relationships; sender inputs, change, amounts and timing remain visible, and co-spending tips can link outputs.

What privacy this demonstrates

Silent payments address one source of linkage: reusing a public receiving address. The sender derives a fresh Taproot output off-chain, without including the recipient's reusable silent-payment address in that output. This is a specific recipient-address privacy property, not a guarantee that every payment relationship is hidden. (Honest limits: sender inputs, change, amounts and timing stay visible, and spending several tips together can link those outputs to each other.)

Broadcast proof on local regtest: a real BIP-352 tip to a dedicated regtest-only receiver — built by the repo's own transaction builder, broadcast, mined, and found by the repo's own receiver scan — runs end to end on a disposable regtest chain below (the transaction builder and scanner are the same code the app uses; UTXO discovery, broadcast transport and block fetching differ).
